# Checkout data model

> **Status:** working document. Defines the shape of `/v0/checkout` payloads, per-item-type fulfilment requirements, validation rules, and how brands declare their checkout requirements in the manifest.
> **Companion docs:** [`security-model.md`](./security-model.md), [`orchestrator-responsibilities.md`](./orchestrator-responsibilities.md), [`why-brand-endpoints.md`](./why-brand-endpoints.md).
> **Last reviewed:** 2026-04-26.

This doc answers the practical question every brand and every consumer agent has to solve before they integrate: **what data must travel at checkout, what's optional, and how does the consumer agent know in advance?**

---

## 1. The shape, top-down

Every `/v0/checkout` request has the same envelope, regardless of item type:

```json
POST /v0/checkout
Authorization: Bearer <consumer-agent JWT>
Content-Type: application/json

{
  "quoteToken":      "<HMAC-signed token returned from /v0/quote>",
  "idempotencyKey":  "<uuid v4, generated by the consumer agent>",

  "user":        { /* always required, see §2 */ },
  "fulfilment":  { /* item-type specific, see §4 */ },
  "payment":     { /* always required, see §3 */ },

  "userIdentityAssertion": "<optional JWT from a trusted IdP>",
  "metadata":              { /* optional, brand-passthrough */ }
}
```

Three blocks always exist (`user`, `fulfilment`, `payment`). Two are optional (`userIdentityAssertion`, `metadata`). Everything else lives inside the three blocks.

---

## 2. The `user` block — always required

Three fields. Every checkout, every item type, every brand.

| Field | Type | Constraint |
|---|---|---|
| `user.name` | string | 1–200 chars, trimmed, non-empty after trim |
| `user.phone` | string | E.164 format (`+<country><number>`, no spaces) |
| `user.email` | string | RFC 5322, lowercased before storage |

That's it. Brands MUST NOT require additional fields in `user`. If a brand needs more (passport, GST number, age), it goes in `fulfilment` or `userIdentityAssertion`.

**Why so minimal:** these three are the irreducible coordination set — name for the courier/staff to greet by, phone for delivery/booking confirmation calls, email for the order receipt. Everything else is conditional on what's being bought.

**Validation:** the consumer agent's orchestrator MUST validate format before submitting. Brand returns `user_field_invalid` (closed enum) if any of the three are malformed.

---

## 3. The `payment` block — always required

| Field | Type | Notes |
|---|---|---|
| `payment.processorRef` | enum | `razorpay` \| `stripe` \| `applepay` \| `googlepay` \| `<future>` |
| `payment.methodToken` | string | Token issued by the processor — never raw card data |
| `payment.threeDSResult` | object \| null | If 3DS was performed, the resulting authentication object |

The brand never sees raw card numbers. Tokenisation happens on the consumer-agent side via the user's payment processor. OpenKarta is payment-rail-agnostic; it carries the token, not the card.

If the brand cannot accept the chosen `processorRef`, it returns `payment_processor_not_supported` and lists its accepted processors in the error payload (closed-enum extension). The consumer agent then re-tokenises with a supported processor.

---

## 4. The `fulfilment` block — item-type specific

`fulfilment` is a discriminated union keyed by `itemType` (and, for `product` and `service`, by `mode`). The consumer agent reads the brand's manifest to know which shape to produce.

### 4.1 `product`, mode `delivery`

```json
"fulfilment": {
  "itemType": "product",
  "mode": "delivery",
  "shippingAddress": {
    "line1":      "string, required, ≤200 chars",
    "line2":      "string, optional, ≤200 chars",
    "city":       "string, required",
    "state":      "string, required (ISO 3166-2 subdivision code preferred)",
    "postalCode": "string, required, format per country",
    "country":    "ISO 3166-1 alpha-2, required",
    "landmark":   "string, optional, ≤200 chars"
  },
  "deliveryInstructions": "string, optional, ≤500 chars",
  "preferredDeliverySlot": "ISO8601 interval, optional"
}
```

### 4.2 `product`, mode `pickup`

```json
"fulfilment": {
  "itemType": "product",
  "mode": "pickup",
  "pickupLocationId": "string — one of the IDs returned in the brand's manifest",
  "pickupTime":       "ISO8601 timestamp, optional (default: ASAP)"
}
```

### 4.3 `product`, mode `digital`

```json
"fulfilment": {
  "itemType": "product",
  "mode": "digital"
}
```

Nothing else needed — the digital good is delivered to `user.email`.

### 4.4 `flight`

Airlines are strict. Names must match passport exactly; mistakes cost real money to fix and can result in denied boarding.

```json
"fulfilment": {
  "itemType": "flight",
  "passengers": [
    {
      "title":        "Mr",                    // Mr | Ms | Mrs | Mstr | Dr (closed enum)
      "givenNames":   "Karan Kumar",            // first + middles, EXACTLY as on passport
      "surname":      "Naidu",                  // EXACTLY as on passport
      "dob":          "1995-05-12",             // ISO date
      "gender":       "M",                      // M | F | X (closed enum)
      "nationality":  "IN",                     // ISO 3166-1 alpha-2
      "passport": {
        "number":         "A12345678",
        "countryOfIssue": "IN",                 // ISO 3166-1 alpha-2
        "expiry":         "2030-05-12"          // ISO date
      },
      "frequentFlyer": {                        // optional
        "airline":  "AI",                       // IATA carrier code
        "number":   "1234567890"
      },
      "specialRequests": ["VGML", "WCHR"],     // IATA SSR codes — optional
      "seatPreference":  "window"               // window | aisle | middle | none — optional
    }
  ],
  "contact": {                                  // contact for THIS booking, may differ from user
    "phone": "+91 98xxxxxxxx",
    "email": "karan@calmosis.com"
  }
}
```

**Strict validation rules** (orchestrator MUST enforce locally; brand MUST also enforce):

| Rule | Reason |
|---|---|
| `givenNames` and `surname` MUST match `^[A-Z ]+$` after uppercasing | IATA character set; tickets strip everything else, leading to passport mismatch |
| `givenNames.length ≥ 2`, `surname.length ≥ 2` | No abbreviations on tickets — IATA / airline policy |
| `passport.expiry` MUST be > 6 months from any flight segment date | International travel rule |
| `dob` MUST be a valid past date; infants/children may have separate fare classes per `quoteToken` | Pricing depends on age category |
| `nationality`, `passport.countryOfIssue`: ISO 3166-1 alpha-2 only | No free-text countries |
| `passport.number` MUST match country-specific regex (orchestrator carries the regex set) | Catches typos before submit |
| Once `/v0/checkout` succeeds, name corrections MUST go through `cancel + re-book`, NOT a partial update | Ticketing systems don't support post-issue field edits |

### 4.5 `stay`

```json
"fulfilment": {
  "itemType": "stay",
  "checkIn":  "2026-05-15",                     // ISO date
  "checkOut": "2026-05-18",                     // ISO date
  "guests": [
    {
      "fullName":          "Karan Naidu",
      "dob":               "1995-05-12",        // optional unless required by brand
      "nationality":       "IN",                // optional unless required by brand
      "governmentId": {                         // required for foreign nationals in India (Form C)
        "type":   "passport",                   // passport | aadhaar | driver_license | national_id
        "number": "A12345678",
        "countryOfIssue": "IN"
      }
    }
  ],
  "specialRequests": "string, optional, ≤500 chars",
  "estimatedCheckInTime": "ISO8601 time, optional"
}
```

`governmentId` requirement is brand-declared in the manifest (e.g., Indian hotels MUST collect it for foreign guests by law).

### 4.6 `bus`

```json
"fulfilment": {
  "itemType": "bus",
  "passengers": [
    {
      "fullName": "Karan Naidu",
      "age":      30,
      "gender":   "M",                          // M | F | X
      "seatId":   "U7",                         // one of the seats locked in /v0/quote
      "governmentId": {                         // required for international routes
        "type":   "passport",
        "number": "A12345678"
      }
    }
  ],
  "boardingPointId": "string — one of the IDs returned in the brand's manifest",
  "droppingPointId": "string — one of the IDs returned in the brand's manifest"
}
```

### 4.7 `service`, mode `at_customer`

```json
"fulfilment": {
  "itemType": "service",
  "mode": "at_customer",
  "serviceAddress": { /* same shape as shippingAddress in 4.1 */ },
  "appointmentTime": "ISO8601 timestamp",
  "specialInstructions": "string, optional, ≤500 chars"
}
```

### 4.8 `service`, mode `at_provider`

```json
"fulfilment": {
  "itemType": "service",
  "mode": "at_provider",
  "appointmentTime": "ISO8601 timestamp",
  "providerLocationId": "string — required if brand has multiple locations"
}
```

### 4.9 `service`, mode `online`

```json
"fulfilment": {
  "itemType": "service",
  "mode": "online",
  "appointmentTime": "ISO8601 timestamp"
}
```

Meeting link goes to `user.email` after order confirmation.

## 5. How brands declare their checkout requirements

The consumer agent must know — *before* it ever calls `/v0/checkout` — what fields it needs to collect from the user. The brand declares this in `/v0/discover` (the manifest):

```json
{
  "agentId": "halcyon-air",
  "supportedItemTypes": ["flight"],
  "itemTypes": {
    "flight": {
      "checkoutSchema": "https://api.halcyon-air.example.com/v0/schemas/flight-checkout.json",
      "checkoutSchemaVersion": "1.0.0",
      "userFieldsRequired": ["name", "phone", "email"],
      "userIdentityAssertion": "optional",
      "acceptedIdentityProviders": ["google.com", "apple.com", "digiyatra.gov.in"],
      "acceptedPaymentProcessors": ["razorpay", "stripe"],
      "additionalConstraints": {
        "minHoursBeforeDeparture": 2,
        "maxPassengersPerBooking": 9,
        "infantPolicy": "see brand T&C"
      }
    }
  }
}
```

**Required fields per item type are not free-form.** The brand picks from the canonical set defined in this doc (§4) — the manifest just says "for this item type, here's the URL of the JSON Schema you should fetch and validate against locally."

The schema is fetched once, cached (24h default), and used by the orchestrator to:

1. Generate the prompt list for the consumer agent UI.
2. Validate locally before submission.
3. Surface field-level errors in the user's UI without a round-trip to the brand.

---

## 6. Validation responsibilities

| Layer | Responsibility |
|---|---|
| Consumer agent UI | Collects answers from the user. Renders error messages. |
| Orchestrator (client-side) | Schema-validates the assembled payload against the brand's `checkoutSchema` BEFORE submitting. Catches missing fields, wrong formats, IATA character violations, expired passports, etc. |
| Brand endpoint (server-side) | Re-validates everything. Never trusts the client. Also performs business-rule checks the client can't (seat still available, fare still valid, inventory still in stock). |

Schema validation on the client is for fast UX. Business-rule validation on the server is for safety.

---

## 7. Closed-enum errors at checkout

Brand returns one of these (HTTP 422 unless noted):

| Error | Meaning |
|---|---|
| `quote_token_invalid` | Signature failed |
| `quote_token_expired` | TTL exceeded |
| `quote_token_already_used` | Idempotency-key mismatch on a previously-checkout'd quote |
| `idempotency_key_conflict` | Same key, different payload |
| `user_field_invalid` | One of `user.name`/`phone`/`email` malformed (closed enum extension lists which) |
| `fulfilment_schema_violation` | Payload didn't match the declared schema. Error includes `path` and `message`. |
| `fulfilment_business_rule_violation` | E.g., passport expired < 6 months from travel, seat unavailable, slot taken. Closed-enum reason. |
| `payment_processor_not_supported` | Brand doesn't accept the chosen `processorRef` |
| `payment_authorisation_failed` | Processor declined the charge |
| `inventory_unavailable` | Item is no longer available since `/v0/quote` |
| `pricing_changed` | Brand-side reprice — should be rare since `quoteToken` should freeze price; if it happens, brand returns the new price + a fresh quoteToken to re-confirm |
| `identity_assertion_required` | Brand requires `userIdentityAssertion` and none was attached |
| `identity_assertion_invalid` | Assertion failed verification |
| `consumer_agent_not_allowed` | Brand allowlist rejected the calling consumer agent (see security-model.md §6) |

## 8. Cross-cutting rules

1. **No partial updates.** A submitted checkout that succeeded cannot be amended in-place. Subsequent changes go through `/v0/orders/:id/cancel` + a fresh `/v0/quote` + `/v0/checkout`.
2. **Idempotency is mandatory.** Every consumer agent MUST send `idempotencyKey`. Brands MUST honour it for at least 24 hours.
3. **Currencies are integer minor units.** Always. No floats, ever.
4. **All timestamps are ISO 8601 with explicit timezone offsets.** No naked local times.
5. **Brand never sees raw payment card data.** Tokens only.
6. **Consumer agent never stores brand-side order data.** Status, history, etc. always come from `/v0/orders/:id/status`.

## 9. Open questions

These should be resolved before this doc becomes normative.

1. **Should `userIdentityAssertion` carry profile data the brand should trust over `user.{name,phone,email}`?** E.g., if Google says the user's verified email is `karan@gmail.com` but the agent submitted `karan@calmosis.com`, who wins? Recommendation: brand prefers the assertion when present, but warns the consumer agent.
2. **Should infants/children on flights be a separate object in `passengers[]` with a different shape, or a `type: 'infant'` discriminator within the same shape?** Current draft: same shape with `dob` driving age category. Open to changing if airlines push back.
3. **Multi-currency carts.** Currently forbidden by spec — every line in the cart must be the same currency. Should we allow per-line currency for international flight bookings? Recommendation: no; force consumer agent to do FX conversion before quote.
4. **Group bookings.** A 9-passenger flight booking is one `/v0/checkout`. A 50-room corporate hotel booking probably isn't. Where's the cutoff, and do we need a separate `groupBooking: true` mode? Defer to v0.5.
5. **`metadata` block — is it brand-passthrough opaque, or do we standardise common fields (UTM, agent-tier, etc.)?** Recommendation: opaque in v0.4, may standardise later.
