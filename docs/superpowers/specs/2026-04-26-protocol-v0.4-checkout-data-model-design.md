# Protocol v0.4 — Checkout data model

**Status:** design approved 2026-04-26
**Sub-plan:** 1 of 3 in the v0.4 protocol bump (this doc + later: orchestrator v0.4, consumer-agent identity RFC-0001)
**Tracks:** A (Merchants), B (Developers)
**Roadmap position:** new plan, slots between Plan 02 (shipped) and Plan 03 (hosted registry). Does not depend on Plan 03 — can ship in parallel.

---

## 1. Goal

Replace the v0.1 `/v0/checkout` request body with a structured three-block envelope (`user` / `fulfilment` / `payment`) plus per-item-type fulfilment shapes, so that:

- Brands receive everything they need to fulfil an order — name/phone/email always, plus item-specific fields (shipping address, passenger names, check-in dates, etc.) — without inventing custom JSON shapes per brand.
- Consumer agents have a single canonical schema per item type to collect against, with brand-declared overrides for narrowing or extending.
- The schema is enforceable: validated client-side by the orchestrator and server-side by the brand, with closed-enum error codes when something fails.

This is a **hard breaking change** from v0.1. URL paths move from `/v0/...` to `/v0.4/...`. The two existing reference agents not migrated by this plan (`reference-agent-stays`, `reference-agent-travel`) stay on v0.1 and are flagged as known-broken in the registry pending follow-up plans.

## 2. Non-goals

- **Consumer-agent identity** (Ed25519 keypair, JWT-per-request, registry key issuance) — Sub-Plan 3, depends on Plan 03.
- **Orchestrator public API** (`createOrchestrator`, `validateCheckoutPayload`, `getCheckoutRequirements`, `watchStatus`) — Sub-Plan 2, depends on this plan.
- **Quote-token signing format change** — out of scope, format unchanged.
- **Item type schemas** (`packages/spec/src/items/`) — out of scope, catalogue shapes untouched.
- **Backwards compatibility with v0.1.** Hard break. v0.1 brands keep working at `/v0/...` if they don't redeploy; the orchestrator stops sending traffic to them once it learns from the manifest that they're on v0.1.

## 3. Architecture

Three layers of change:

**Spec layer** (`@openkarta/spec`)
- New schemas: `CheckoutRequestBody`, `UserBlock`, `PaymentBlock`, `Fulfilment` (9-shape discriminated union).
- Manifest gains optional `checkoutSchema` (JSON Schema) and required `protocolVersion: "0.4"`.
- 14 new closed-enum errors.
- New `protocol-version.ts` with `PROTOCOL_VERSION` and `URL_PREFIX` constants — single source of truth.

**SDK layer** (`@openkarta/sdk-node`)
- Route paths move to `/v0.4/...` in both server helpers and client.
- New `validateCheckoutBody(brandManifest, body)` helper that merges spec base + brand `checkoutSchema` and validates.

**Reference layer** (`packages/reference-agent-shop`)
- Halcyon Shop migrates fully to v0.4 — accepts new body, declares `checkoutSchema` narrowing `product.delivery` to require its specific shipping fields, redeployed to `halcyon-shop.fly.dev`.
- Other two reference agents (`reference-agent-stays`, `reference-agent-travel`) stay on v0.1.

## 4. The schemas

### 4.1 CheckoutRequestBody (envelope)

```ts
type CheckoutRequestBody = {
  user: UserBlock;                          // always required
  fulfilment: Fulfilment;                   // always required, discriminated by itemType + mode
  payment: PaymentBlock;                    // always required
  userIdentityAssertion?: IdentityAssertion;// optional — populated when consumer agent has verified identity
  metadata?: Record<string, string>;        // brand-defined extras, ignored unless declared in checkoutSchema
};
```

### 4.2 UserBlock

```ts
type UserBlock = {
  name: string;        // 1–200 chars, trimmed
  phone: string;       // E.164 format, regex enforced
  email: string;       // RFC 5322 simplified regex
};
```

This is the **always-required minimum**. Brand may not relax these via `checkoutSchema`. Brand may add extra required fields via override (e.g. corporate account ID).

### 4.3 PaymentBlock

```ts
type PaymentBlock = {
  processorRef: "razorpay" | "stripe" | "cashfree" | "paypal" | "cod";
  methodToken: string; // opaque, processor-issued — never raw card data
};
```

Closed enum. Adding a new processor requires a spec bump.

### 4.4 Fulfilment (9 shapes)

Discriminated by `itemType` + `mode`:

| `itemType` | `mode` | Required fields |
|---|---|---|
| `product` | `delivery` | `address: ShippingAddress`, `deliverySlot?: ISO8601Range` |
| `product` | `pickup` | `pickupLocationId: string`, `pickupSlot?: ISO8601Range` |
| `product` | `digital` | `deliveryEmail?: string` (defaults to `user.email`) |
| `flight` | — | `passengers: FlightPassenger[]`, `contactEmail?: string` |
| `stay` | — | `guests: StayGuest[]`, `checkIn: ISO8601Date`, `checkOut: ISO8601Date`, `specialRequests?: string` |
| `bus` | — | `passengers: BusPassenger[]`, `boardingPointId: string` |
| `service` | `at_customer` | `address: ServiceAddress`, `slot: ISO8601Range` |
| `service` | `at_provider` | `slot: ISO8601Range` |
| `service` | `online` | `joinEmail?: string` (defaults to `user.email`), `slot: ISO8601Range` |

#### FlightPassenger (IATA-strict)

```ts
type FlightPassenger = {
  title: "MR" | "MRS" | "MS" | "MISS" | "DR" | "MSTR";
  givenNames: string;            // A-Z + space, no abbreviations, matches passport
  surname: string;               // A-Z + space
  dob: ISO8601Date;
  gender: "M" | "F" | "X";
  nationality: ISO31661Alpha2;
  passport?: {
    number: string;
    countryOfIssue: ISO31661Alpha2;
    expiry: ISO8601Date;         // must be > 6 months from travel date
  };
  frequentFlyer?: { airline: IATAAirlineCode; number: string };
  specialRequests?: string[];    // SSR codes
  seatPreference?: "WINDOW" | "AISLE" | "ANY";
};
```

`givenNames` and `surname` regex: `/^[A-Z ]+$/`. Brand-side validation rejects mixed-case, hyphens, accents — IATA convention.

`StayGuest`, `BusPassenger`, `ShippingAddress`, `ServiceAddress` are simpler; full shapes in `packages/spec/src/fulfilment.ts`.

### 4.5 Manifest additions

```ts
type Manifest = {
  // ...existing fields...
  protocolVersion: "0.4";        // new: required
  checkoutSchema?: JSONSchema7;  // new: optional, narrows or extends spec base
};
```

## 5. Validation model — spec base + brand override

Both orchestrator and brand validate. Brand is authoritative.

**Merge rule:**
1. Start with spec base schema for `(itemType, mode)`.
2. If `manifest.checkoutSchema` is present, apply as a JSON Schema override:
   - Brand may **add** required fields beyond spec base.
   - Brand may **mark optional** fields that spec base marks required, EXCEPT the `UserBlock` fields (`name`, `phone`, `email`) which are non-negotiable.
   - Brand may **tighten** field constraints (e.g. `passport.expiry` must be > 12 months instead of > 6).
   - Brand may **NOT** loosen field types or remove non-User required fields wholesale.
3. Resulting merged schema is what both sides validate against.

The merge is implemented in `packages/sdk-node/src/validate-checkout.ts` and exported for both orchestrator and brand server use.

## 6. Errors (14 new closed-enum codes)

| Code | When |
|---|---|
| `E_PROTOCOL_VERSION_UNSUPPORTED` | Brand sees a request to a path/version it doesn't speak |
| `E_USER_NAME_INVALID` | name empty, > 200 chars, or non-string |
| `E_USER_PHONE_INVALID` | phone fails E.164 regex |
| `E_USER_EMAIL_INVALID` | email fails RFC 5322 regex |
| `E_FULFILMENT_TYPE_MISMATCH` | e.g. `fulfilment.itemType: "flight"` sent to a product-only brand |
| `E_FULFILMENT_REQUIRED_FIELD_MISSING` | a required field for the merged schema is absent |
| `E_FULFILMENT_FIELD_INVALID` | a field is the wrong type or fails its constraint |
| `E_FULFILMENT_PASSENGER_NAME_INVALID` | flight/bus passenger name fails IATA regex |
| `E_FULFILMENT_PASSPORT_EXPIRED_OR_EXPIRING` | passport expiry inside the threshold window |
| `E_FULFILMENT_ADDRESS_UNSERVICEABLE` | brand cannot deliver/serve the given address |
| `E_PAYMENT_PROCESSOR_UNSUPPORTED` | brand doesn't accept the given `processorRef` |
| `E_PAYMENT_METHOD_TOKEN_INVALID` | processor rejects the token |
| `E_CHECKOUT_SCHEMA_VIOLATION` | catch-all when JSON Schema merge validation fails; `details.path` carries the failing field |
| `E_QUOTE_TOKEN_INVALID` | existing v0.1 code, kept |

Format: `{ error: { code, message, details? } }`. HTTP status: 400 for validation, 409 for conflict (e.g. unserviceable), 422 for processor rejection, 410 for unsupported version.

## 7. URL paths

All brand endpoints move from `/v0/...` to `/v0.4/...`:

```
/v0.4/discover
/v0.4/search
/v0.4/get
/v0.4/quote
/v0.4/checkout
/v0.4/orders/:id/status
/v0.4/orders/:id/cancel
/v0.4/orders/:id/return
```

`/v0/...` paths are not served by v0.4 brands. Orchestrator reads `manifest.protocolVersion`, picks the matching `URL_PREFIX`, refuses to send traffic if the prefix isn't recognised (`E_PROTOCOL_VERSION_UNSUPPORTED` raised client-side).

## 11. Open questions

1. **Should `checkoutSchema` be JSON Schema draft 7 or 2020-12?** Draft 7 is more widely supported; 2020-12 is current. Defaulting to draft 7 unless you say otherwise.
2. **`metadata: Record<string, string>`** — strings only, or any JSON values? Strings are easier to validate and log; any-JSON gives brands more rope.
3. **Halcyon Shop's `checkoutSchema`** — should it require a `giftMessage` field as a demo of brand-side extension, or stay minimal? Recommendation: include one optional and one required brand-extension field to exercise the merge path.
4. **`reference-agent-stays` and `reference-agent-travel` migration follow-up** — separate one-line-each plans, or bundled into a single "v0.4 reference agent migration" plan? Bundling is faster.
5. **`E_FULFILMENT_PASSPORT_EXPIRED_OR_EXPIRING` threshold** — hard-coded to 6 months in spec, or brand-configurable via `checkoutSchema`? Spec base says 6 months; brand can tighten via override.
